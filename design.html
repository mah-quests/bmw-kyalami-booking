API & Database Design

The application logic layer and the data layer behind RaceDay — the "brain" that validates requests and applies business rules, and the store that holds every user, booking, event and lap time.

Architecture

Standard 3-tier system flow

🖥️ Frontend

Booking screens, login, dashboards. Sends requests, renders responses.

→
⚙️ API

Validates data, applies rules ("Is this event still available?"), connects FE to DB.

→
🗄️ Database

Stores users, bookings, events, lap-time results.

Example flow: Driver clicks "Book Race Event" → API checks event capacity & payment → DB writes a confirmed booking record → leaderboard reads lap times back to the dashboard.

Business rules enforced by the API: no double-booking the same session · reject if event is full · payment must clear before CONFIRMED · only admins create/edit events.

Relationships

drivers 1 — ∞ bookings

A driver makes many bookings over a season.

events 1 — ∞ sessions

Each event splits into morning/afternoon sessions.

sessions 1 — ∞ bookings

Slots per session are capped by slots_total.

bookings 1 — 1 payments

Booking confirms only once payment clears.

Sample DDL

CREATE TABLE bookings (
  booking_id   BIGSERIAL PRIMARY KEY,
  driver_id    BIGINT REFERENCES drivers(driver_id),
  session_id   BIGINT REFERENCES sessions(session_id),
  car_class    VARCHAR(50),
  status       VARCHAR(20) DEFAULT 'PENDING',
  amount_zar   DECIMAL(10,2),
  created_at   TIMESTAMP DEFAULT now(),
  UNIQUE (driver_id, session_id)   -- no double-booking
);
